# ARCHITECTURE — слои, механизм, гейты

## Задача

Один набор знаний и процедур, который разворачивается в **любой** агентский
инструмент и переживает переезд на новую машину. Без жёстких привязок,
но с реальной производительностью: подключается то, что нужно инструменту,
а не всё подряд.

## Слои

```
┌─ ядро (core/) ─────────────────────── не знает ни об одном инструменте ────┐
│  skills/    процедуры со статусом и замером                                │
│  policies/  правила поведения: безопасность, готовность, стиль             │
│  playbooks/ последовательности «как делать X»                              │
│  knowledge/ конспекты и справочники (слой глубокого раскрытия)             │
└────────────────────────────────────────────────────────────────────────────┘
                                    │  трансляция, без своей политики
┌─ адаптеры (adapters/<инструмент>/) ────────────────────────────────────────┐
│  куда класть скиллы, как называется файл инструкций, какие особенности     │
└────────────────────────────────────────────────────────────────────────────┘
                                    │  ссылки, не копии
┌─ инструменты ──────────────────────────────────────────────────────────────┐
│  DeepSeek Harness · Hermes · Codex · Gemini CLI · OpenCode · Claude Code   │
└────────────────────────────────────────────────────────────────────────────┘
```

**Правило слоя:** адаптер **не содержит политики**. Он умеет только переводить
ядро на язык инструмента. Если в адаптере появляется правило поведения — оно
должно быть в ядре, иначе оно не доедет до остальных инструментов.

## Точка встречи

`~/.agents/skills` — каталог, который читают **разные** инструменты:
DeepSeek Harness 0.2+ читает его нативно (переменная `DSH_AGENTS_HOME`),
та же конвенция у `bb` и других. Ядро ставится туда один раз; адаптеры добавляют
ссылки только там, где инструмент ищет скиллы в другом месте.

Это снижает дублирование: один скилл → одна ссылка в общей точке → доступен всем,
кто её читает.

## Почему ссылки, а не копии

| Копии | Ссылки |
|---|---|
| правка расползается по N местам | правка одна, видна сразу всем |
| версии расходятся незаметно | расхождение невозможно по построению |
| непонятно, что главное | источник правды один — репозиторий |
| нужно синхронизировать | синхронизировать нечего |

Цена: инструмент, который не умеет следовать ссылкам, получит их как обычные
каталоги (это нормально); на файловых системах без симлинков потребуется копирование
и гейт дрейфа (`harness doctor`).

## Манифест и почему формат ограничен

`harness.yaml` — **единственное** место, где записано, что куда кладётся.
Путей, зашитых в скрипты, нет.

Формат намеренно беден: вложенные словари по отступам, списки `- `, простые скаляры.
Никаких якорей, inline-массивов и блочных скаляров. Причина практическая:
обвязка должна разворачиваться на **голой** машине, а тащить парсер YAML ради
одного файла — значит поставить развёртывание в зависимость от пакета, которого
может не быть. Установщик разбирает манифест сам, а `doctor` проверяет, что разбор
дал ожидаемую форму, — ошибка формата становится громкой, а не тихой.

## Установка, обновление, уборка

| Команда | Что делает | Когда |
|---|---|---|
| `harness detect` | показывает, какие инструменты есть на машине | первым делом на новой машине |
| `harness install [инструмент]` | создаёт ссылки ядра в найденных инструментах | после `detect` |
| `harness doctor` | YAML, дубли имён, коллизии с встроенными командами, битые ссылки | перед работой и после правок |
| `harness outdated` | что изменилось в ядре с момента установки | перед обновлением |
| `harness update` | пересоздаёт ссылки и отпечатки | после изменений |
| `harness prune` | убирает **свои** ссылки на исчезнувшие скиллы | после чистки ядра |
| `harness inventory` | машинный отчёт об установленном | для реестра |

Установщик никогда не перезаписывает то, что не создавал: занятый путь
не трогается, а попадает в отчёт как пропущенный. `prune` удаляет только то,
что записано в состоянии, — чужие файлы и каталоги не задеваются.

Состояние: `~/.harness/state.json` — что, куда и с каким отпечатком поставлено.

## Три раздельные операции вместо одной

`outdated` → `update` → `prune` намеренно разведены. Одна команда «привести всё
в порядок» опасна тем, что делает необратимое молча. Здесь сначала смотрят,
потом применяют, потом убирают лишнее — и на каждом шаге видно, что произошло.

## Гейты (что проверяется автоматически)

1. **Формат скилла.** Фронтматтер разбирается живым парсером; имя — kebab-case;
   `name` и `description` обязательны. Битый YAML = скилл молча исчезает из
   каталога, поэтому это проверяется до установки.
2. **Дубли имён.** Одно имя в двух местах — ошибка: неясно, какая версия победит.
3. **Коллизии с встроенными командами.** Скилл не должен затенять `help`, `compact`,
   `clear` и подобные.
4. **Ссылки.** Каждая записанная ссылка существует и ведёт туда, куда должна.
5. **Секреты.** Репозиторий публичный → `.gitignore` + сканер + чтение `git ls-files`
   глазами (см. `SECURITY.md`).
6. **Доказательность.** Скилл без `EVIDENCE.md` не устанавливается по умолчанию.

## Границы, которые не размываются

- **Ядро не содержит путей конкретной машины.** Только `~` и относительные пути.
- **Адаптеры не содержат секретов** — только имена переменных окружения.
- **Состояние не хранится в репозитории.** Оно машинно-специфично и живёт в `~/.harness`.
- **Репозиторий не знает о проектах.** Обвязка — про инструмент, а не про работу.

## Чего здесь нет намеренно

| Не делаем | Почему |
|---|---|
| Каталог на сотни скиллов | его нельзя перепроверить, а значит нельзя доказать пользу |
| Генерируемые «интеграции» в дереве | второй источник правды, который устаревает |
| Свою версию у каждого скилла, разъехавшуюся с общей | путаница; версия набора + версия скилла, обе видимы |
| Счётчики, вписанные в README руками | расходятся; считать из манифеста |
| Автоустановку без подтверждения | обвязка расширяет полномочия агента |
| Монорепо-инфраструктуру (сборка, тесты продукта) | на порядок больше, чем нужно личной обвязке |

## Путь на новую машину

```bash
# 1. поставить инструмент (любым штатным способом)
# 2. забрать обвязку
git clone https://github.com/StarDust1508/github_harness.git ~/harness
# 3. посмотреть, что есть
~/harness/tools/harness detect
# 4. развернуть
~/harness/tools/harness install all
# 5. проверить
~/harness/tools/harness doctor
```

Секреты, ключи и доступы **не переносятся** этим механизмом: они восстанавливаются
отдельно из менеджера паролей. Обвязка приносит знание и процедуры, не доступы.
