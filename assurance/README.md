# Assurance — работа, результат которой можно проверить

Твоя работа в GRC и в безопасности даёт **не код, а утверждение**: «система
соответствует», «риск под контролем», «защита держит атаку». Ценность такого
утверждения равна нулю, пока его нельзя проверить.

Здесь лежит механика, которая делает утверждение проверяемым. Кода в ней
минимум: **реестры — это данные, правила — это данные, а код только сверяет**.

## Модель

```
утверждение  →  доказательство  →  проверка
   реестр         evidence/         rules.yaml
```

Четыре объекта, связанные ссылками:

| Реестр | Что описывает | Ключ |
|---|---|---|
| `systems.yaml` | ИИ-системы: назначение, роль, класс риска по AI Act | `id` |
| `risks.yaml` | риски: владелец, обработка, остаточный уровень, дата пересмотра | `id` |
| `controls.yaml` | меры: что закрывают, чем доказаны | `id` |
| `findings.yaml` | находки внутреннего аудита: статус, срок, проверяющий | `id` |
| `audit-program.yaml` | программа аудита: что и как проверяем, что этим подтверждаем | `id` |

Связи: риск → система, мера → риск, находка → мера, доказательство → файл.

## Почему так, а не «папка с документами»

Папка с документами не отвечает на вопросы, которые задаёт аудитор:
«у этого риска есть владелец?», «эта мера чем-то подтверждена?»,
«у высокорисковой системы есть вся техдокументация?», «этот срок уже прошёл?».

Реестр отвечает — потому что он **данные**. Один и тот же файл служит
и рабочим продуктом (его показывают аудитору), и входом проверки.

## Свобода системы

Правила не зашиты в код. Что обязательно, что от чего зависит, какие бывают
значения — всё в `rules.yaml`. Новая предметная область добавляется **файлом
правил, а не программированием**.

Минимальный язык правил — пять конструкций:

| Правило | Смысл |
|---|---|
| `require` | поля, которые обязаны быть заполнены |
| `require_if` | поля, обязательные при условии (`equals` или `in` — набор) |
| `ref` | ссылка на запись другого реестра (проверяется, что существует) |
| `evidence` | поля-ссылки на файл доказательства (проверяется, что файл есть) |
| `not_past` | поля-даты, которые не должны быть в прошлом |
| `ref_any` | ссылка на запись любого из перечисленных реестров |
| `covered_by` | запись обязана кем-то проверяться |

## Оценка риска: принятие — это решение

Шкала и аппетит вынесены в `risk-appetite.yaml`: вероятность, воздействие,
матрица пересечения и пороги. Это решение организации, а не универсальная
норма, поэтому лежит отдельно от правил проверки.

Проверяемая часть — не оценка (её честность машина не оценит), а **след
решения**:

```
✗ risks/risk-cv-bias: при residual=medium обязательно «accepted_by»
```

Риск выше аппетита можно принять — но это решение, у которого есть имя
и причина. Риск без принятия это не «принятый риск», а забытый, и на внешнем
аудите он становится находкой.

Что проверка **не** делает: не оценивает, честна ли оценка и действительно ли
остаточный уровень ниже исходного. Подменять работу человека проверкой нельзя,
и это записано в правилах явно.

## Внутренний аудит: покрытие важнее списка

Программа аудита — это набор **проверок**, а не чек-лист. У каждой указано:
что смотрим, как смотрим, какое доказательство ожидаем и **что она подтверждает**
(`verifies` — мера или ответ).

Из этого поля работает проверка, которой раньше не было:

```
controls/ctl-cv-bias-testing: не проверяется ни одной процедурой аудита
```

**Мера, которую не проверяет никто, существует только на бумаге.** Это опаснее
отсутствующей меры: об отсутствующей известно, а о такой думают, что она есть.
Поэтому `covered_by` входит в проверку мер наравне с наличием доказательства.

Находка аудита ссылается на процедуру, из которой пришла. Без этой связи через
полгода невозможно понять, находка случайная или проверка систематически слепа.

## Ответы на security-вопросники

Отдельная предметная область, добавленная **без единой строки кода** — потому
что движок правил уже умел всё нужное:

```
вопросник клиента  →  ссылки  →  библиотека ответов  →  доказательства
   его формулировки              один ответ на всех        файлы
```

Клиенты спрашивают одно и то же разными словами. Ответ даётся один раз —
с доказательством — и переиспользуется. Ответы разным клиентам не расходятся,
а расхождение в ответах первое, что находит внешний аудит.

| Правило | Что ловит |
|---|---|
| `ref` на библиотеку | вопрос, ссылающийся на несуществующий ответ |
| `evidence` | ответ «да, выполняем» без ссылки на документ |
| `require_if status=partial` | частичное выполнение без срока закрытия |

Проверка честности здесь важнее, чем где-либо: смягчённая формулировка читается
опытным аудитором как сокрытие и стоит дороже самого пробела.

## Проверка

```bash
tools/harness check              # все реестры
tools/harness check systems      # один реестр
```

Проверка отвечает на вопрос «можно ли это показывать аудитору» и возвращает
ненулевой код, если нет. Она же стоит в pre-commit и в CI.
