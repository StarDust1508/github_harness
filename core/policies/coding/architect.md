# Фаза архитектуры

Главная задача — **проектировать**, а не писать код. Исследовать пространство решений, избегать локальных оптимумов, создавать надёжные планы.

## 1. Классификация задачи

- **Greenfield** — новый компонент/приложение с нуля
- **Targeted Refactoring / Feature Addition** — улучшение существующего кода. **Первый шаг — изучить `AppGraph.xml`** для понимания архитектуры и зависимостей

## 2. Плейбук структурированной разработки

### Шаг 0: STUDY_EXECUTORS (Изучение возможностей исполнителей)

Перед проектированием изучить правила из `rules/`:
- `rules/code.md` — возможности и ограничения фазы реализации
- `rules/debug.md` — возможности фазы отладки
- `rules/orchestrator.md` — возможности делегирования субагентам

Это необходимо для понимания, что именно можно делегировать и как.

### Шаг 1: THINK_AND_CLARIFY (Стратегическая неопределённость)

Не фиксироваться на первом решении. Сначала сформировать пространство критериев.

1. Уточнить у пользователя конечные намерения
2. Сформулировать 3-5 ключевых критериев успеха (скорость, RAM, читаемость, зависимости...)
3. При необходимости — создать `business_requirements.md`

### Шаг 2: CHOOSE_TECH_STACK

- Приоритет надёжным библиотекам (stdlib, numpy, pandas, scipy, sklearn...)
- В `requirements.txt` — комментарий к каждой библиотеке: ПОЧЕМУ выбрана
  ```
  pandas==2.0.0 # Сложные join'ы (Критерий: Скорость трансформации)
  ```
- Если requirements.txt уже есть — консерватизм, добавлять только необходимое
- Для незнакомых библиотек — Context7 MCP для актуальной документации

### Шаг 3: PROPOSE_CONCEPT (Суперпозиция → Коллапс)

1. 2-3 принципиально разных варианта решения
2. Оценка каждого по критериям из Шага 1
3. Запросить у пользователя выбор
4. Явно подтвердить: "Приступаю к варианту Б"

**Пример рассуждения:**
> *Критерии:* 1. Скорость старта. 2. Мин. RAM. 3. Простота.
> *Гипотеза А (In-Memory БД):* Идеально по скорости, но нарушает RAM.
> *Гипотеза Б (SQLite + Индексы):* Средний старт, минимальный RAM, нативно.
> *Вывод:* Гипотеза Б — глобальный оптимум.

### Шаг 4: DESIGN_AND_VALIDATE_SOLUTION

Создать `DevelopmentPlan.md` со структурой:

1. **Draft Code Graph** — XML-граф компонентов (спецификация: `rules/graph.md`)
2. **Step-by-step Data Flow** — пошаговый поток данных
3. **Acceptance Criteria** — измеримые критерии приёмки

Дождаться одобрения плана.

### Шаг 5: PROPOSE_IMPLEMENTATION

Передать в реализацию (фаза Code) или делегировать субагентам (фаза Orchestrator).

## 3. Обязательные архитектурные паттерны

Любой план ОБЯЗАН включать:

1. **Изоляция слоев** — backend (логика, БД) и frontend (UI) в разных файлах, даже для простых задач
2. **CLI-интерфейс (Agentic UX)** — backend имеет точку входа через `argparse` (паттерн Subcommand Delegation). Контроллеры не содержат `print` — возвращают данные. Вывод CLI — машиночитаемый (JSON)
3. **Тесты + LDD** — pytest с выводом логов `IMP:7-10`. Тесты не "тихие" — показывают контекст выполнения
4. **Headless UI-тесты** — вызывать обработчики напрямую, без запуска сервера (Gradio и т.п.)

## 4. Шаблоны

При создании проектных документов использовать официальные шаблоны:

- **DevelopmentPlan.md** → `rules/template_dev_plan.md`
- **Проектные документы** (бизнес-требования, спецификации) → `rules/template_document.md`
- **XML-граф кода** (AppGraph.xml) → `rules/graph.md`
