# Базовые принципы и протокол взаимодействия

## 1. Протокол взаимодействия

- **Пользователь** = Архитектор и Оркестратор (определяет требования, стратегию)
- **агент** = Автономный Исполнитель (полная ответственность за генерацию кода)
- Код ревьюится на соответствие согласованным протоколам и форматам разметки
- Семантические структуры (теги, якоря) — специально спроектированные сигналы для навигации по коду. Не "упрощать" их

## 2. Ключевые принципы

### 2.1. Полнота генерации (нулевая терпимость к сокращениям)
Запрещено использовать `...`, `pass`, `и т.д.`, `# остальной код`. Всегда генерировать полный код.

### 2.2. Суперпозиция и Коллапс
При неоднозначной проблеме **НЕ писать финальный код сразу**. Сначала сформулировать 2-3 гипотезы/варианта решения, обсудить с пользователем, затем реализовать выбранный вариант.

### 2.3. Пространственная навигация (XML-DOM для кода)
Оборачивать логические узлы кода в парные теги:
```python
# START_BLOCK_INITIALIZE: Инициализация данных
...code...
# END_BLOCK_INITIALIZE

# START_BLOCK_PROCESS: Обработка результатов
...code...
# END_BLOCK_PROCESS
```

**Критерий сегментации:**
- Complexity > 7 → сегментация через START-END блоки обязательна
- Complexity <= 7 → сегментация опциональна, но рекомендуется

### 2.4. Семантический экзоскелет
Писать алгоритм естественно (DRY, модульность), но помещать в семантические контейнеры (теги блоков, контракты).

### 2.5. Малые модули
Предпочитать разделение кода на небольшие модули/файлы. Семантическая разметка в малых модулях не является существенным оверхедом.

### 2.6. Семантическая разметка экономит бюджет токенов
Вывод о том, что семантическая разметка в коде приводит к перерасходу бюджета — **ложный**. Токены чтения в 10 раз дешевле токенов генерации. Если неверно понять контекст из-за ложной экономии, лишний цикл отладки приведёт к большему перерасходу. Семантическая разметка — это инвестиция в надёжность. Встроенная документация в коде экономит контекст по сравнению с документацией отдельно от кода.

## 3. Правило "Шрама на коде"

При исправлении бага добавлять:
```python
# BUG_FIX_CONTEXT: [почему старый подход не работал и почему выбран текущий]
```

## 4. Навигация по проекту

- **AppGraph.xml** — высокоуровневая карта проекта (обновлять после изменений)
- От графа к коду: AppGraph → модуль → MODULE_MAP → START_FUNCTION
- От лога к коду: `[BLOCK_NAME]` в логе → search по BLOCK_NAME
- При модификации обновлять: MODULE_MAP, CONTRACT, CHANGE_SUMMARY, теги блоков
