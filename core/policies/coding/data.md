# Работа с данными (ETL)

Оптимальные стратегии для задач трансформации данных с SQL и Python/Pandas.

## 1. Pandas-First (стратегический уровень)

- Pandas — прозрачный пошаговый "калькулятор" с контролем промежуточных результатов
- **Ограничения:**
  - Память: миллионы строк → OutOfMemory
  - Циклы `iterrows` — катастрофически медленны
  - Цикл с SQL внутри — антипаттерн (N+1)
- Если данные большие или нужны итеративные вычисления → переход к SQL-first (п. 3)

## 2. Рекомендации по Pandas

### Безопасная загрузка
- **Идеально:** однотабличный `SELECT ... FROM ... WHERE ...`
- **Относительно безопасно:** JOIN одного уровня. Сразу после загрузки — диагностика: `COUNT(*)` из исходных таблиц vs `len(df)` (проверка на декартово произведение)

### Нормализация
- Избегать строковых JOIN — работать с целочисленными ключами
- `astype('category')` для строковых колонок с низкой кардинальностью

### Эффективные манипуляции
- Векторизация: `.groupby()`, `.apply()`, `pd.merge()`, арифметика над колонками
- `iterrows` допустим для ≤ 5000 строк
- Цикл с SQL внутри — не более 100-200 итераций

### Выгрузка в БД (паттерн "Временная таблица")
1. Сформировать итоговый DataFrame с колонкой `EditState` (`'I'`, `'U'`, `'D'`)
2. Выгрузить в промежуточную таблицу: `df.to_sql()` в одной транзакции
3. SQL-запросы: `INSERT ... SELECT ...`, `UPDATE ... FROM ...` из промежуточной в основную
4. **Не удалять промежуточную таблицу** — очищать в начале следующего запуска

## 3. SQL через промежуточные таблицы (SQL-first)

Для больших данных — SQL в процедурном стиле, эмулируя пошаговость Pandas:

1. **Фильтрация:** `CREATE TABLE filtered_data AS SELECT * FROM ... WHERE ...`
2. **Обогащение:** `CREATE TABLE enriched_data AS SELECT ... FROM filtered_data JOIN ...`
3. **Агрегация:** `CREATE TABLE aggregated_data AS SELECT ..., SUM(...) FROM enriched_data GROUP BY ...`

**Принцип эскалации:** начинать с простых запросов, при проблемах — максимальное расщепление на шаги.

## 4. Принцип "Большой код из малых простых блоков"

- Не писать короткие и сложные выражения — акцент на логическую простоту блока
- DRY может быть антипаттерном: предпочтителен линейный код с умеренной повторяемостью
- Вместо DRY — структурирование через `START-END` теги
