# Аудит агентской обвязки

Симптомы «агент не пользуется инструментами», «врёт, что сделал» и «стало хуже»
почти всегда объясняются не моделью, а обвязкой. Этот скилл — процедура, которая
находит причину в фактах: журналах сессий, коде установки и конфигурации.

## Железное правило

**Не начинать с мнения о причине.** Сначала числа по журналам, потом гипотеза,
потом проверка гипотезы в коде. Порядок обратный — это гадание.

## Шаг 1. Снять базовые числа по журналам

Журналы сессий — единственный источник, который не врёт. Для DeepSeek Harness они
лежат в `<DSH_HOME>/sessions/<экранированный-cwd>/<session-id>/session.v*.jsonl.zstd`.

**Ловушка №1, стоит многих часов:** файл журнала — это **склейка независимых
zstd-кадров** (по одному на каждую дозапись). `zlib.zstdDecompressSync()` в Node
возвращает **только первый кадр**, то есть одну строку-заголовок. Любая статистика,
собранная так, покажет нули и будет выглядеть как «данных нет».
Распаковывать только потоково: `zstd -d -c <файл>`.

Считать по каждому журналу:

- `tool/call` и `tool/result` по `callId` — сколько вызовов, сколько **без** результата;
- `tool/result` с `isError: true` — доля ошибок **по каждому инструменту отдельно**
  (общая доля врёт: `bash` с 0,03 % маскирует `web_fetch` с 10 %);
- разбивка по неделям — тренд важнее среднего;
- ходы, где ассистент писал намерение, но вызова не было;
- события `llm/retry` и их коды: сетевые сбои (`TRANSPORT`, `SERVER`) — это не отказ модели;
- признаки компрессии и усечения результатов.

## Шаг 2. Проверить, не обманывает ли интерфейс

Прежде чем обвинять агента в бездействии, исключить, что работа **скрыта отображением**:

- режим ленты по умолчанию может **сворачивать карточки вызовов** (в DSH до 0.2 это
  был `compact`; в 0.2 дефолт — `detailed`);
- у инструментов без специального рендерера карточка общая и свёрнутая;
- ошибка инструмента может помечаться только цветом, без текста «failed»;
- вызовы внутри подагентов в ленту родителя **не попадают вообще**.

Если хоть один пункт верен — симптом «агент не берёт инструменты» может быть
полностью объяснён восприятием. Проверять это ДО форензики кода.

## Шаг 3. Найти «тихие» механизмы в коде установки

Искать целенаправленно, по классам:

1. **Подмена результата.** Обёртки, которые дожидаются выполнения и затем заменяют
   уже успешный результат ошибкой (таймаут-политики).
2. **Необратимое отключение.** Логика вида «после N неудач снять регистрации» —
   инструменты исчезают до перезапуска процесса, а в лог уходит одна строка.
3. **Ложная атрибуция.** Тексты ошибок, приписывающие решение человеку
   («пользователь отклонил»), когда человека не спрашивали.
4. **Скрытие собственных действий.** Компрессия, которой велено не упоминать,
   что контекст сжат; усечение результатов без указания, где взять полный.
5. **Состояние в памяти вместо диска.** Защиты вроде «правка только после чтения»,
   чьё состояние не переживает перезапуск или не общее с подагентом.
6. **Проглоченные ошибки.** `catch {}` и `logger.warn` там, где отказ должен менять
   поведение: инструмент формально есть, но не работает.

Каждую находку фиксировать как: симптом → механизм → файл:строка → условие
срабатывания → как проверить → лечение.

## Шаг 4. Проверить версии и дрейф

- Установленная версия против последней опубликованной; **отдельно проверить, по
  какому тегу смотреть** — у части пакетов тег `latest` отстаёт и даёт ложную картину.
- Битые симлинки и затенение: два экземпляра одного пакета в разных `node_modules`
  ломают проверки тождества объектов.
- Патчи и форки: что именно меняют, привязаны ли к версии, что будет при обновлении.

## Шаг 5. Проверить бюджет контекста

- Размер глобальных инструкций: они стоят токенов **в каждом запросе**.
- Есть ли в цепочке файл, который в бюджет не влезает: тогда обвязка **молча
  отбрасывает широкие файлы**, и часть правил до модели не доходит.
- Стоимость схем инструментов: посчитать на реальном запросе из журнала
  (`request/header`), а не на глаз.

## Шаг 6. Отчёт

Реестр проблем по слоям, у каждой: уровень (блокер / деградация / шум),
доказательство, способ проверки, лечение. Отдельным разделом — то, что
**не подтвердилось**: отрицательный результат тоже результат и защищает от
повторного расследования.

## Признаки, что аудит сделан плохо

- Выводы без чисел и без путей к файлам.
- Гипотеза «модель стала хуже» без проверки обвязки.
- Отчёт, в котором нет ни одного опровергнутого подозрения.
- Рекомендации, которые нельзя проверить командой.

## Связанное

- `EVIDENCE.md` рядом — замер, на котором основан скилл.
- Политика `evidence-before-skill` в ядре: без замера скилл не подключается.
